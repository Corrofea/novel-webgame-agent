# 游戏化设计：从小说到游戏数据

## 输入
- `runtime/<书>/bible/world.md`（世界观圣经）
- `runtime/<书>/characters.json`（人物卡）
- `templates/game_modes/<mode_id>.json`（模式模板，已选定）
- `templates/themes/<theme_id>.json`（主题模板）

## 输出（直接写入 games/<书>/data/）
1. `game.js` —— 元数据（title/entry/save_key）
2. `mode.js` —— 模式配置（按模式模板 runtime 节填充）
3. `characters.js` —— 游戏用角色数据
4. `scenes.js` —— 场景图（核心）
5. `theme.js` —— 主题实例

**Schema 以 `templates/game_folder/data/*.js` 的文件头注释为唯一权威**，生成前必须先读它。

## 流程

### 1. 设计 brief（深模型执行）
读 bible + 模式模板，产出设计 brief（写入 runtime/<书>/design/brief.md）：
- 游戏名与副标题（来自小说气质）
- 玩家扮演：谁/视角（S4 为多视角列表）
- 核心机制落地：模式模板的 mechanics 如何在本书中具体化
- 属性清单（含好感度对象与理由）：3~6 个为佳，id 用英文
- 决策点清单：10~40 个（G1），列出原文位置、选项设计、分支走向
- 结局结构：2~5 个结局，说明汇聚方式
- 场景数预算：短篇 15~40 个，长篇按卷 ×15~25

### 2. 场景图设计（同一调用中产出）
- 节点 id 规则：`s001` 起，连续编号，不改写已生成节点
- 入口节点必须是"立刻给玩家第一个选择"的场景
- 分支回收规则：分支 2~3 个节点内必须汇合回主干（除非通向结局）
- 每节点 2~3 个选项；选项文案必须具体（拒绝"接受/拒绝"式空泛选项，要写"收下手帕"这种可感知行动）
- 好感度阈值效果：`affection_x >= N` 解锁专属场景/结局分支
- 伏笔回收：S3 模式每条线索有放置点与使用点；G1 模式伏笔在结局前回收
- 结局条件：用属性门槛 + 关键 flag 组合表达，保证 2~5 个结局都可达成

### 3. 生成数据文件
- scenes.js 严格按 schema 生成；narration 用原文改写压缩（保留原文味道，控制在每场景 60~200 字）
- effects 数值克制：好感度单次 ±1~3，重要抉择 ±5~8
- 引用一致性：所有 attr id 出自 mode.js；所有角色 id 出自 characters.js；所有 goto 指向已规划节点
- 长篇按卷分批生成：每批独立上下文，批量开头附"已有节点 id 清单与关键 flag 状态"

### 4. 质量自检（生成后立即自查）
- [ ] 每个节点有 choices/auto/ending 至少其一
- [ ] 无孤立节点（所有节点从 entry 可达）
- [ ] 无死路（每个非结局节点有可用选项）
- [ ] 结局数量与 mode.js endings 一致
- [ ] narration 不含剧本标记（如"[旁白]"、"作者注"）
- [ ] 数据为合法 JSON/JS，无截断

## 注意事项
- **忠于原著是底线**：选项可以扩展原文未写的走向，但必须符合人物性格与世界观；结局不得违反原文设定的硬性事实（S4 旁批除外——那是对比阐释）
- 好感度对象选"与主角互动最深"的角色，最多 3 个，过多玩家会疲劳
- 分支爆炸是最大的失败模式：宁可砍分支也不堆节点
- 玩家体验优先：前 3 个场景必须出现一次选择、一次属性变化反馈
